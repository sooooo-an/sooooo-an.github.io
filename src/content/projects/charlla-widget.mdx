## 배경

찰나는 커머스 사이트에 숏폼 비디오 위젯을 얹어주는 B2B SaaS다. 위젯은 남의 사이트 안에서 동작하기 때문에, 우리 쪽 코드가 호스트 페이지의 성능과 동작에 직접적인 영향을 준다. 멀티샵플레이어, 슬라이드, 플로팅, 히어로배너 등 여러 위젯 유형을 제공하면서 이 영향 범위가 계속 넓어졌다.

## 문제 정의

가장 큰 문제는 한 페이지에 위젯이 여러 개 올라갈 때 비디오가 동시에 로드되면서 호스트 페이지 전체가 무거워지는 것이었다. 여기에 더해 위젯 코드가 앱 배포에 묶여 있어서, 위젯만 고치고 싶어도 전체 배포 사이클을 타야 했다.

## 실패 조건

- 호스트 페이지의 로딩 성능을 눈에 띄게 떨어뜨리면 실패
- 웹과 iOS·Android WebView 중 한 곳에서라도 동작이 갈리면 실패
- 위젯 수정 한 줄 때문에 콘솔/플레이어 전체를 다시 배포해야 하면 실패

## 접근

로딩 문제는 "동시에 몇 개의 비디오가 살아 있는가"를 통제하는 문제로 정의했다. active source를 동기화하고 화면에서 벗어난 비디오의 버퍼를 해제하는 방식으로, 동시 로드되는 비디오 수를 80% 이상 줄였다.

위젯과 호스트 페이지 사이 통신은 postMessage 기반으로 옮겼는데, 웹과 iOS·Android WebView의 동작 차이가 실제 장애로 이어질 수 있는 영역이라 Playwright E2E로 환경별 차이를 검증하면서 진행했다.

## 구현

- 위젯 스크립트를 앱 배포에서 분리해 CDN으로 독립 배포하고, 해시 기반 버전 관리를 붙였다
- iframe 기반이던 콘솔 프리뷰 구조를 pnpm 모노레포의 `widget-core` 패키지로 전환해, 콘솔과 플레이어가 동일한 렌더링 로직을 공유하도록 했다

## 결과

동시 로드 비디오 수가 80% 이상 줄었고, 위젯은 앱 배포와 무관하게 독립적으로 배포할 수 있게 됐다. 콘솔 프리뷰와 실제 플레이어의 렌더링이 같은 코드에서 나오면서 "콘솔에서는 되는데 실제로는 다르게 보이는" 류의 문제도 줄었다.

## 배운 점

남의 페이지 위에서 도는 코드는 내 서비스의 기준이 아니라 호스트 페이지의 기준으로 판단해야 한다. 그리고 플랫폼별 차이는 "될 것 같다"로 넘기면 반드시 운영에서 터지기 때문에, 검증 가능한 형태로 만들어두는 게 결국 더 빠르다.

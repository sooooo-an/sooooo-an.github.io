AI Shorts를 구현하는 중에 당황스러운 일을 마주했다.

히어로배너 위젯을 만들 때와 똑같이 했다. 기획서 링크를 복사해서 넣고, Figma를 붙이고, 만들어달라고 했다. 그때는 멀쩡한 코드가 나왔다. 그런데 AI Shorts를 만들고 나서 코드를 열어보니 달랐다. 블록 중복이 늘어 있었고, `useEffect`가 여기저기 붙어 있었고, 컴포넌트 하나에 모든 기능이 들어가 있었다.

가장 이상했던 건 이거였다. 컨테이너에 있던 상태를 Form으로 내리고 submit만 컨테이너에서 처리하고 싶었다. 값은 파라미터로 받으면 된다.

```tsx
// 내가 원한 구조
function Container() {
  const handleSubmit = (values: ShortsFormValues) => {
    createShorts(values);
  };
  return <Form onSubmit={handleSubmit} />;
}
```

돌아온 코드는 이랬다.

```tsx
// 받은 구조
function Container() {
  const formRef = useRef<FormHandle>(null);

  const handleSubmit = () => {
    const values = formRef.current?.getValues();
    createShorts(values);
  };
  return <Form ref={formRef} />;
}

const Form = forwardRef<FormHandle, Props>((props, ref) => {
  const [values, setValues] = useState(initialValues);
  useImperativeHandle(ref, () => ({ getValues: () => values }));
  // ...
});
```

동작은 한다. 상태도 Form이 들고 있다. 요청을 지켰다고 볼 수도 있다. 그런데 내가 없애려던 결합이 그대로 남았다. 컨테이너는 여전히 Form의 내부를 알고 있고, 이제는 ref라는 더 불편한 경로로 알고 있다.

이런 걸 하나하나 고치다 보니 어느 순간 이상한 상태가 되어 있었다. **내가 프롬프트로 구조를 설명하고, 클로드는 받아 적기만 했다.** 판단하는 쪽이 전부 나로 넘어와 있었다. 이대로 고쳐 쓰면 다음 프로젝트도 똑같아질 게 뻔했다. 코드를 고치는 대신 클로드를 다시 똑똑하게 만들어야 했다.

## 왜 이렇게 됐는지부터 찾았다

터미널에서 `/resume`로 AI Shorts를 만들던 세션의 트랜스크립트를 찾았다. 그 기록을 그대로 넣고 물었다. 이 코드가 어떤 경로로 이렇게 됐냐고. 답은 이랬다.

> 기획서와 Figma를 프레임 단위로 받아 한 화면에 쌓음 → 처음부터 한 컴포넌트 구조가 됨 → 그 위에 API·재사용·이어받기 같은 동작이 추가됨 → effect와 컴포넌트 구조를 제한하는 규칙이 없어서, 모델이 기본 습관대로 "state 변화에 반응하는 effect"로 끼워 넣음 → 지금 코드

시작점이 문제였다. Figma 프레임을 순서대로 붙이면 "화면 하나"가 기준이 된다. 화면이 기준이면 컴포넌트도 하나로 시작한다. 그 위에 기능이 붙을 때마다 쪼갤 이유가 없으니 계속 안으로 들어간다.

## 의존성 배열이 자라는 과정

가장 선명한 증거는 등록 로직에 있던 `useEffect`였다.

```tsx
useEffect(() => {
  const task = generation.task;

  if (!task || task.status !== 'DONE'
      || !generation.taskId || registerStarted) {
    return;
  }

  useAiTaskStore.getState().markShortsRegisterStarted();
  freePhotoQuota.reset();

  if (libraryFull) {
    generation.detach();
    show({ /* 한도 초과 안내 */ });
    return;
  }

  registration.mutate({ /* ... */ });
}, [
  t, registerStarted, generation.task, generation.taskId,
  generation.input, registration.mutate, freePhotoQuota,
  libraryFull, generation.detach, show,
]);
```

의존성이 10개다. 한 번에 이렇게 짠 게 아니라 **요구사항이 하나 붙을 때마다 한 줄씩 자랐다.**

| 날짜 | deps | 늘어난 이유 |
|---|---|---|
| 08-31 | 4 | 최초 — 생성 요청·폴링·노출 게이트 |
| 08-31 | 5 | 무료 화보 몫을 "영상 1건당"으로 |
| 09-04 | 7 | 한도 초과 안내를 AlertPopup으로 |
| 09-07 | 8 | 문구를 lang 키로 |
| 09-15 | 9 | 안내 뒤 작업을 세션에서 끊기 |
| 09-21 | 10 | 등록 표시를 store로 |

3주 동안 6번에 걸쳐 4에서 10이 됐다. 그동안 한 번도 "이 배열 왜 이렇게 길지"를 묻지 않았다.

## 어떤 근거로 이렇게 됐나

### 1. 시작은 옳았다

트리거가 클릭이 아니라 폴링 결과였다. "DONE이 되면 등록한다"의 출발점이 쿼리 응답이라 이벤트 핸들러를 걸 자리가 없었다. 외부 값 변화에 반응하는 자리는 이펙트가 맞다.

### 2. 반응과 하는 일을 한 곳에 뒀다

트리거는 `task.status === 'DONE'` 하나인데, 하는 일을 전부 본문에 넣었다. 표시 남기기, 무료 몫 리셋, 한도 분기, 팝업, 등록 요청까지.

이펙트 본문에서 읽는 값은 **전부 의존성이 된다.** 그래서 기능이 하나 붙을 때마다 배열이 따라 자랐다. 위 표가 그 기록이다.

### 3. 린터가 그걸 정당화해줬다

`exhaustive-deps`가 빠졌다고 하면 넣었다. 그 규칙은 **동기화 코드의 정확성**을 검사하는 건데, 이건 동기화가 아니라 일회성 이벤트였다.

규칙은 "이 배열이 옳은가"를 검사하지 **"이 코드가 이펙트여야 하는가"는 묻지 않는다.** 린터가 초록불이면 설계도 맞다고 여긴 게 실수다.

### 4. 아무도 아프지 않았다

`registerStarted` 가드가 재실행을 무해하게 만들어서, 배열이 10개가 되도록 증상이 없었다. 되돌아볼 계기가 없었다.

## 같은 조건으로 새로 만들어봤다

원인을 알았으니 대조군이 필요했다. 같은 의존성, 같은 디자인 시스템으로 새 프로젝트를 만들고 같은 기능을 요청했다.

```
app/(with-appbar)/ai-shorts/layout.tsx
├─ AiTaskRunner kind="shorts"    렌더 없음 · 폴링 → DONE이면 라이브러리 등록
├─ AiTaskRunner kind="photo"     렌더 없음 · 폴링
├─ AiShortsLnb                   탭 · 클릭 시 이탈 가드
└─ {children}
   ├─ shorts/page.tsx → AiShortsScreen → AiShortsFormProvider (Formik)
   │    ├─ (왼쪽) AiShortsForm
   │    └─ (오른쪽) flow.status 하나에 패널 하나
   │         idle / generating / registering / done / failed
   └─ photo/page.tsx → 동일 구조
```

내 코드와 비교하면 세 군데가 달랐고, **두 개는 새로 나온 쪽이 나았다.**

**폴링을 layout에 뒀다.** 내 구조는 폴링이 화면 안에 있어서 탭을 옮기면 멈춘다. 작업은 sessionStorage에 남아 돌아오면 이어받지만, 떠나 있는 동안 진행이 갱신되지 않고 등록도 안 걸린다. 러너가 layout에 있으면 화면 수명과 무관하게 계속 돈다. 내가 그렇게 안 한 이유는 단순하다. 원래 화면 하나가 다 들고 있었고, 나는 그걸 쪼개기만 했지 "폴링이 화면 수명에 묶여야 하나"를 묻지 않았다.

**폼을 Provider로 풀었다.** 내 방식은 `useImperativeHandle`로 밖에서 `submit()`을 부른다. 그래서 dirty·uploading·durationSec을 위로 올리는 `onStatusChange` 콜백이 남아 있다. Provider면 오른쪽 패널도 폼 값을 직접 읽어서 그 미러가 필요 없다.

**상태를 하나로 모았다.** `flow.status` 하나로 패널이 갈린다. 내 쪽은 store의 `run.outcome`으로 갈린다. 여기는 사실상 같은 곳에 도착했고 이름만 다르다.

## 프롬프트를 이렇게 바꿨다

달랐던 건 모델이 아니라 **입력**이었다. 예전에는 기획서만 넣고 "계획 세워봐"라고 했다. 지금은 세 단계로 나눈다.

### 0. 규칙은 프롬프트가 아니라 파일에 둔다

프롬프트로 한 말은 `/compact`를 거치면 흐려진다. AI Shorts 세션은 한 달 동안 이어졌고 압축도 여러 번 됐다. 그 사이에 내가 정한 원칙들이 조용히 사라졌다.

그래서 반복해야 하는 원칙은 `console-react.md` 같은 규칙 파일에 둔다. 프롬프트에는 그때그때의 작업 지시만 넣는다.

### 1. 설계 단계 — 코드 없이 구조만

기획서와 Figma 플로우 전체(진행·완료·실패·모달까지 모든 프레임)를 한 번에 주고, 계획 모드에서 이렇게 요청한다.

> 코드는 쓰지 마. 이 기능의 컴포넌트 트리, 각 상태를 누가 소유하는지(서버 상태 / store / 로컬), 사용자 이벤트와 서버 이벤트가 어디서 처리되는지 표로 정리해줘. `features/ai-shorts/README.md`에 저장해.

여기서 내가 검토하고 확정한다. 이 문서가 이후 세션들의 기준이 되고, 압축이 되더라도 파일로 남는다.

### 2. 뼈대 단계 — 파일만 먼저

> README 구조대로 파일만 만들어. 각 컴포넌트는 props 타입과 빈 마크업만. 부모 화면은 `phase`로 자식을 고르기만 해.

구조가 먼저 서고 나면, 그 안을 채우는 건 모델이 잘한다.

## 정리

클로드가 망가진 게 아니었다. 내가 판단을 안 내린 채로 시켰고, 모델은 빈자리를 자기 기본값으로 채웠다.

바이브코딩의 후유증은 코드가 틀리는 게 아니라 **구조가 나도 모르게 결정되는 것**이다. 그리고 그건 나중에 코드를 고쳐서 되돌릴 수 있는 게 아니라, 시작하는 문서에서 정해진다.

리뷰할 때 신호도 정해뒀다. ref가 새로 생겼거나, 의존성 배열이 눈에 띄게 길어졌거나, 훅이 하나 늘었으면 일단 멈추고 본다. 대부분 구조를 안 바꾸고 우회한 흔적이다.

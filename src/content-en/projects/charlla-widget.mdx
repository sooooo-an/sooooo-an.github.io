## Background

Charlla is a B2B SaaS that provides short-form video widgets embedded on e-commerce sites. Because the widget runs inside third-party websites, our code directly impacts the performance and behavior of the host page. As we expanded our offerings to include various widget types—such as multi-shop players, sliders, floating widgets, and hero banners—the scope of this impact continuously grew.

## Problem Statement

The biggest issue was that when multiple widgets were placed on a single page, videos loaded simultaneously, making the entire host page heavy. On top of that, the widget code was tightly coupled with the main app deployment, meaning even a minor fix to a widget required going through the entire app release cycle.

## Failure Conditions

- Noticeably degrading the loading performance of the host page.
- Any behavioral inconsistency across web, iOS WebView, or Android WebView.
- Having to redeploy the entire console/player just to update a single line of widget code.

## Approach

I framed the loading problem as controlling "how many videos are active simultaneously." By synchronizing active sources and releasing buffers for off-screen videos, I reduced the number of concurrently loaded videos by over 80%.

For communication between the widget and the host page, I migrated to a `postMessage`-based architecture. Since behavioral differences between web and native WebViews (iOS/Android) could easily lead to production incidents, I systematically validated cross-environment behavior using Playwright E2E tests.

## Implementation

- Decoupled widget scripts from app deployment to deploy them independently to a CDN with hash-based version control.
- Refactored the iframe-based console preview structure into a `widget-core` package within a pnpm monorepo, enabling both the console and the live player to share identical rendering logic.

## Results

The number of concurrently loaded videos decreased by over 80%, and widgets can now be deployed independently without relying on main app releases. Furthermore, sharing rendering logic between the console preview and the actual player significantly reduced bugs where "it works in the console but renders differently in production."

## Lessons Learned

Code running on someone else's page must be evaluated against the host page's standards, not our own service's standards. Additionally, brushing off platform-specific edge cases with an assumption that "it should probably work" will inevitably blow up in production—building verifiable test environments from the start is always faster in the long run.

## Background

This project aimed to build an ecosystem enabling external developers to create and publish apps for the collaboration tool Swit. I designed a 3-tier architecture consisting of the Developer Portal, Marketplace, and a Client-Rendering SDK that renders third-party app UIs.

## Problem Statement

The primary challenge was "safely rendering UI definitions provided by third parties within our client." Because it was a Server-Driven UI, we did not directly control the content to render, yet rendering arbitrary content posed significant security risks.

## Failure Conditions

- Failure if arbitrary scripts execute from third-party definitions
- Failure if existing apps break when the SDK version upgrades
- Failure if out-of-order asynchronous responses cause the wrong view to render

## Approach

I explicitly defined the boundaries of what could be rendered. I created a whitelist of 17 allowed block types, falling back to `UnsupportedComponent` for anything else. Only `html_frame`, which required high flexibility, was passed through an iframe paired with DOMPurify, and I restricted the externally exposed surface area using `public-api.ts`.

## Implementation

- **Version Compatibility**: Added an ingestion layer to transform v1 responses into the v2 spec upon arrival, allowing the renderer to operate on a single unified type.
- **Asynchronous Consistency**: Managed views using an app-level stack (hash map + ordered array) and discarded responses if their `view_id` was stale.
- **Decoupling Marketplace and Rendering Engine**: Separated boundaries so changes in the Marketplace would not impact the rendering engine.

## Results

Successfully built a structure where third-party apps run smoothly like native UIs inside the Swit client, while strictly keeping renderable scope controlled within our defined whitelist.

## Lessons Learned

Defining "what to allow" via a whitelist makes security boundaries and specification documentation identical. Additionally, handling version compatibility at the entry point rather than inside the renderer keeps the codebase much simpler.

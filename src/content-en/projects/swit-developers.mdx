## Background

This project aimed to build an ecosystem where third-party developers could create and publish apps on the collaboration tool Swit. I designed a three-layer architecture consisting of a Developer Portal, Marketplace, and a Client-Side Rendering SDK that renders third-party app UIs.

## Problem Definition

The core challenge was: "How do we safely render UI definitions sent by third parties within our client?" Since it was Server-Driven UI, we didn't directly control the content to be rendered, yet rendering arbitrary input poses serious security risks.

## Criteria for Failure

- Failure if arbitrary scripts execute due to third-party definitions
- Failure if existing apps break when upgrading the SDK version
- Failure if race conditions in asynchronous responses cause the wrong view to render

## Approach

I explicitly defined the boundaries of what could be rendered. A whitelist of 17 allowed block types was established, falling back to `UnsupportedComponent` for anything else. Only `html_frame`—which required higher flexibility—was allowed through an iframe with DOMPurify, and the external API surface itself was restricted using `public-api.ts`.

## Implementation

- **Version Compatibility**: Introduced a transformation layer that converts v1 responses to the v2 specification upon receipt, allowing the renderer to handle only a single unified type.
- **Asynchronous Consistency**: Managed views as app-level stacks (hash map + ordered array) and discarded responses if the `view_id` was stale.
- **Decoupling Marketplace and Rendering Engine**: Separated boundaries so that changes in the Marketplace would not impact the rendering engine.

## Results

Created a structure where third-party apps behave like native UIs inside the Swit client, while strictly keeping renderable components within our defined whitelist.

## Lessons Learned

Defining "what to allow" via a whitelist makes the security boundary and the spec documentation one and the same. Additionally, handling version compatibility at the entry point rather than inside the renderer keeps the code significantly simpler.
